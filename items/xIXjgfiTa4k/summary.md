## [핵심 내용]
커뮤니티에서 화제가 된 '동네 치과의 AX 전환기'(치과 원장이 DGX Spark 12대로 원내 로컬 AI를 구축한 사례)에 영감을 받은 영상이다. 1인 유튜버가 협찬받은 미니PC GEEKOM IT13 Max 1대에 자기 업무 자동화 시스템을 올려 본다. 기능은 다음과 같다. 네이버 메일 연동 후 로컬 LLM(Qwen3.5 4B, Ollama)으로 협업·스팸·기타 분류, 음성 알림, YouTube Data·Analytics API로 채널 지표 수집, 파이썬 워커로 통계 처리 → 로컬에서 민감정보 마스킹 → 클라우드 AI(Codex)로 채널 적합성 판단과 답장 초안 작성, 계약서 OCR(엠바고·제한 조건 추출), 일정·할 일·칸반 자동 생성, LLM 위키 축적, 디스코드 리포트. 핵심 설계 원칙은 "메모리가 작은 미니PC는 가벼운 분류만 로컬 LLM에, 숫자 계산은 파이썬에, 높은 추론은 클라우드에 맡기되 마스킹 후 보낸다"이다. 결론: 미니PC로도 AX 서버는 "충분히 가능"하지만 고성능 로컬 LLM은 못 돌리므로 클라우드와 섞어야 한다. 마지막은 국내 3년 A/S와 윈도우 기본 탑재라는 제품 장점(광고성)으로 마무리한다.

## [주요 주장]
- 00:06 도입: 단톡방에서 공유받은 '치과 의사가 로컬 LLM으로 AX 시스템을 구축한 사례'. 댓글에 '주작'이라는 의견이 많지만, 주작 여부보다 구현했을 때 사업에 이득이 되느냐가 중요하고, 그 점은 주작이라고 한 사람들도 동의할 것이다. 영감을 준 글로 본다.
- 01:05 제품 스펙(협찬 홍보 구간, 요약): 인텔 코어 울트라, 16코어 22스레드라 멀티태스킹에 유리. 하우징 설계 덕에 발열 해소가 잘 됨(IT12 리뷰 때도 느낌). 2.5G 랜포트 2개(홈서버용), 디스플레이 출력 C타입 2개 + HDMI 2개로 최대 4대 모니터 연결. 유휴 전력이 낮다. 윈도우 기본 탑재 → 윈도우 환경에서 구현.
- 02:09 연동 항목: 네이버 메일, 로컬 LLM, 음성 알림(제일 재밌었던 기능), 채널 방향성(AI 분석용), 유튜브 채널(지표), 디스코드(리포트 수신).
- 02:45 메일 분류: 협업·스팸·기타. 로컬 LLM Qwen3.5 4B를 썼는데, 작은 모델이라 걱정했지만 메일 분류는 잘한다. 메일이 오면 음성으로 알려 준다.
- 03:12 유튜브 연동: YouTube Data API + YouTube Analytics API로 지표를 불러온다. 주간 리포트는 파이썬 워커로 지표 추출·통계 → 마스킹 → 클라우드 AI 분석.
- 03:33 마스킹 이유: 분석에 높은 추론이 필요해 클라우드 AI에 맡기는데, 업체 기밀·개인정보가 클라우드로 넘어가면 안 되므로 로컬에서 마스킹한다. 한계: 알고리즘이 숫자를 전부 가려 메모리 용량(GB) 같은 것까지 마스킹된다. 개선 중.
- 04:09 마스킹 후 채널 적합성 판단(외부 AI) → 답장 초안 작성. 협업 진행 시 프로젝트화하고, 메일에서 일정·할 일을 인식해 캘린더 등록과 투두리스트를 만든다. 아이템 분석 기능도 넣었지만 아직은 사람이 직접 하는 게 품질이 낫다.
- 04:44 계약서: OCR로 텍스트만 추출하고, 계약서가 있으면 그 내용을 일정·할 일에 최우선 반영한다. 한 줄씩 분석해 요구사항, 엠바고, 제한 조건, 영상 필수 포함 사항을 뽑는다. 이 분석은 로컬 Qwen 4B급으로도 충분했다. 처리 내역은 위키로 만들어 다른 분석에 재활용한다.
- 05:49 미니PC가 AX 서버가 될 수 있나: "충분히 가능, 단 제한 조건 있음." 치과 사례는 DGX Spark 12대를 사서 4대씩 묶어 GLM·DeepSeek을 돌렸는데, 지금 12대를 사면 1억이 넘는다. IT13 Max는 CPU·그래픽은 준수하지만 메모리가 제한적이라 로컬에서 다 할 수 없다.
- 06:39 설계: 업무를 잘게 쪼개 추론이 적게 드는 분류는 로컬 LLM에 우선 배치. 수치 추출·계산은 파이썬 워커에 맡겨 LLM은 분석만 한다(리소스·시간 절감). 아이템 분석과 메일 초안처럼 높은 추론은 Codex에 붙였다. 치과처럼 민감한 의료정보를 다루지 않으니 Codex와 로컬 LLM 혼합으로 만족스러운 품질이 나왔다.
- 07:38 설치: Git(버전 관리), Node.js(패키지), Python(워커), Ollama(로컬 LLM), Docker Desktop(DB) → 개발 서버 실행 → 웹 접속 → 관리자 비밀번호 생성.
- 08:25 시연: 네이버 메일·Codex 연결, 채널 방향성 입력 → 테스트 메일이 '협업'으로 분류되고 민감정보가 노란색으로 마스킹됨 → Codex로 채널 적합성 진단 → 메일 초안 → LLM 위키에 저장 → 프로젝트화(일정·할 일 자동 생성, 아이디어·계약서 관리) → 캘린더, 칸반 보드.
- 09:32 총평: CPU가 좋아 로컬 LLM과 AX 서비스를 함께 돌려도 쾌적했다. 발열 관리가 좋아 스로틀링 걱정이 없고, 전력이 적어 24시간 서버로 둘 만하다. 고성능 로컬 LLM은 못 돌리지만 Codex와 결합하면 업무에 붙일 수준이다.
- 10:24 (광고성) "알리에서 싼 미니PC 사면 되지?" → 사업장에는 국내 3년 A/S와 윈도우 기본 탑재(전원만 꽂으면 사용)가 직구보다 큰 장점이다.

## [현재 프로젝트와 연결 가능성]
- 크루즈 사업(3)·크루즈 AI: 승객 PII를 다루는 업무(예약 메일, 여권·명단, 선사 계약서)에 "로컬 소형 LLM으로 분류·마스킹 → 마스킹본만 클라우드 고성능 모델로 추론" 구조를 그대로 참고할 수 있다. 저장소 정책(PII 금지)과도 맞는 방향이다. 다만 영상 속 마스킹은 숫자를 무차별로 가리는 초기 수준이라, 실제 적용하려면 정밀한 PII 탐지가 필요하다.
- 계약서 OCR → 엠바고·제한 조건·의무사항 자동 추출 → 일정·할 일 등록 흐름은 선사·전세선 계약 관리(하드블럭 조건, 취소 기한)에 응용할 수 있다.
- 이사님 봇 운영(2): "숫자는 파이썬이 계산, LLM은 해석만" 원칙은 리포트형 봇 작업의 정확도·비용 관리에 유효하다(치과 사례도 같은 원칙).
- 원본인 '동네 치과의 AX 전환기'(arca.live, gatsbydds) 자체가 이 영상보다 연구 가치가 크다. 사내 포털·전화 AI·보험 서류 대조·승인 게이트·에이전트 분업 구조가 담겨 있다.

## [추가 연구 추천 여부]
- Level 1. 협찬 제품 리뷰에 개인 업무 자동화 데모를 붙인 영상이라 새 기법은 적다. 다만 원본 '동네 치과의 AX 전환기' 시리즈(1~3편)는 Level 2로 따로 읽어 볼 가치가 있다. 크루즈 사업 사내 AX(PII 로컬 처리 + 클라우드 추론, 승인 게이트)의 레퍼런스로 연구원 2·3에 넘길 것을 권장한다.
