### 2-2. 인터뷰와 외부 자료가 다른 점

## 3부. 바로 쓰는 노하우

### 3-1. 원칙 12가지

1. **"만들어 줘" 대신 "인수인계"로 생각합니다.** 새로 온 유능한 직원에게 일을 넘긴다고 보고 씁니다(인터뷰 31:33, S7).
2. **문제부터 씁니다.** 무엇이 불편하고 누가 왜 곤란한지가 첫 줄입니다. 해결책은 그다음입니다(41:40 '불평쟁이').
3. **'무엇'과 '어떻게'를 나눕니다.** 이사님은 무엇, 왜, 어디까지(PRD)를 쓰고, 기술 선택은 개발팀이나 AI의 계획서에 맡깁니다(S1).
4. **이번에 안 하는 것(비목표)을 꼭 적습니다.** AI는 적지 않은 것까지 친절하게 만들어 버립니다(S11, S10).
5. **완료 기준은 확인할 수 있게 씁니다.** "편하게" 대신 "○○하면 ○○가 보인다"처럼 씁니다. 그대로 테스트가 됩니다(S2, S5).
6. **AI에게 먼저 질문하게 합니다.** 빈 문서 앞에서 고민하지 말고 AI의 인터뷰에 답하시면 됩니다. 손으로 쓴 메모 사진을 줘도 됩니다(17:52, 16:50, S3).
7. **작게 나눠 하나씩 끝냅니다.** 첫 버전은 화면 1~2개, 흐름 1개로 합니다. 하나가 돌아가면 구조가 보입니다(26:56, S7, S9).
8. **증거로 확인합니다.** "다 됐습니다"라는 말 대신 화면 캡처, 테스트 결과, 샘플 데이터를 받습니다(S3).
9. **금지선과 승인선을 정합니다.** 항상 할 것 / 먼저 물어볼 것 / 절대 하지 말 것 세 칸입니다. 돈, 외부 발송, 고객 정보, 실서버가 여기에 들어갑니다(S9, S7).
10. **알아야 할 사람에게만 알려 줍니다.** 업무나 에이전트별로 필요한 정보만 줍니다. 계약 수치나 고객 정보는 필요한 곳에만 둡니다(25:56, S6).
11. **결정은 한 줄씩 기록합니다.** "10/27 결정: 1차에는 결제 제외. 이유: 파트너 정산 미확정." 이렇게 남기면 AI나 사람이 바뀌어도 흔들리지 않습니다(S12).
12. **문서는 살아 있게 둡니다.** 만들다 바뀐 것은 PRD에 바로 반영합니다. 오래된 문서는 틀린 지시가 됩니다(S1, S9, S4).

### 3-2. 문서는 세 장으로 나눕니다

| 문서 | 누가 | 담는 것 | 비유 |
|---|---|---|---|
| **PRD(요구사항)** | 이사님 (AI가 질문하며 정리) | 문제, 사용자, 목표·비목표, 핵심 흐름, 완료 기준, 금지선 | "무엇을, 왜, 어디까지" — 인수인계서 |
| **기술 계획서(Tech Spec / plan)** | 개발팀 또는 AI (이사님은 요약만 확인) | 기술 선택, 데이터 구조, 외부 연동, 위험 요소, 테스트 방법 | "어떻게" — 작업 설계도 |
| **작업 목록(Tasks)** | AI가 만들고 개발팀이 검토 | 하나씩 끝내고 확인할 수 있는 작은 작업들, 순서, 각 작업의 완료 기준 | "오늘 할 일" — 체크리스트 |

여기에 **결정 기록(Decisions)** 한 장과, 에이전트가 매번 읽는 **짧은 기본 지침(AGENTS.md/CLAUDE.md)**이 더해집니다(S4, S6, S12).

### 3-3. PRD 템플릿 (이사님용)

> 아래 [예시]는 이해를 돕기 위해 지어낸 **가상의 '크루즈 블록 특가몰'** 내용입니다. 실제 계약 조건, 요금, 일정이 아닙니다. 실제 수치는 비공개 저장소에만 두고 PRD에는 "별첨 참조"로 적습니다.

```markdown
# PRD: <프로젝트 이름>   (버전 0.1 · 작성 <날짜> · 작성자 <이름> · 상태: 초안/검토/확정)

## 1. 한 줄 요약
- 무엇을: 누구를 위해 무엇을 만드는지 한 문장
- [예시] 미리 확보한 크루즈 객실 블록 중 남은 객실을, 가입 회원에게 기간 한정 특가로 보여 주고 예약 문의를 받는 웹페이지

## 2. 왜 하나요 (문제)
- 지금 무엇이 불편하고, 그래서 무엇을 놓치는지
- [예시] 출발이 가까워진 잔여 객실을 담당자가 전화·메신저로 한 분씩 안내하느라 시간이 들고, 안내가 늦어 객실이 비는 경우가 있다

## 3. 누가 쓰나요 (사용자)
- 주 사용자 / 내부 사용자 / 관리자
- [예시] 고객: 크루즈 경험이 있는 기존 회원(모바일 위주) · 내부: 예약 담당자(문의 확인·회신) · 관리자: 특가 등록 담당자

## 4. 목표와 성공 기준
- 목표: 2~3개
- 성공 판단: 숫자나 관찰할 수 있는 사실로
- [예시] 목표: ① 잔여 객실 안내 시간 단축 ② 문의를 한곳에 모으기
- [예시] 성공: 특가 등록부터 페이지 노출까지 담당자 혼자 10분 안에 끝낼 수 있다 · 모든 문의가 관리 화면 한곳에 쌓인다

## 5. 이번에 안 하는 것 (비목표)
- 목표가 될 법하지만 이번에는 일부러 빼는 것
- [예시] 온라인 결제 · 실시간 재고 자동 연동 · 회원가입 신규 개발(기존 회원 명단 사용) · 영문 페이지

## 6. 핵심 흐름 (사용자 이야기)
- "<누구>로서 <무엇>을 하고 싶다, <왜>냐하면" 형식으로 3~7개
- [예시] 고객으로서 출발일·선실 등급별 특가를 한눈에 보고 싶다. 내 일정에 맞는지 빨리 판단하려고
- [예시] 고객으로서 마음에 드는 특가에 이름·연락처·인원을 남겨 문의하고 싶다
- [예시] 담당자로서 새 문의가 오면 바로 알고, 회신 상태(대기·안내 완료·성사)를 표시하고 싶다
- [예시] 관리자로서 특가를 등록·마감하고, 마감된 특가는 고객 화면에서 자동으로 내리고 싶다

## 7. 완료 기준 (확인할 수 있게)
- "~하면 ~된다" 형식. 개발팀은 이걸 그대로 테스트로 씁니다
- [예시] 관리자가 특가를 '마감'으로 바꾸면 → 1분 안에 고객 화면에서 사라진다
- [예시] 고객이 연락처 없이 문의를 누르면 → "연락처를 입력해 주세요"가 뜨고 접수되지 않는다
- [예시] 문의가 접수되면 → 담당자 화면에 '대기'로 표시되고, 고객에게 "접수되었습니다" 화면이 보인다

## 8. 화면·데이터 (아는 만큼만)
- 필요한 화면 목록, 꼭 보여야 할 항목. 손그림 사진 첨부도 좋습니다
- [예시] 화면: 특가 목록 / 특가 상세 / 문의 폼 / 담당자 문의함 / 관리자 특가 등록
- [예시] 특가 항목: 선박·항로(일반명), 출발일, 선실 등급, 특가 표시 여부, 남은 객실 수(대략 표시), 마감일
- [예시] 요금·계약 조건: "별첨(비공개) 참조" — PRD 본문에 적지 않음

## 9. 지켜야 할 것 · 금지선
- ✅ 항상 / ⚠️ 먼저 물어보기 / 🚫 절대 금지
- [예시] ✅ 고객 정보는 문의 처리 목적에만 쓰고, 화면에 연락처 전체를 노출하지 않는다
- [예시] ⚠️ 고객에게 메일·문자 자동 발송, 외부 서비스 추가, 요금 표시 방식 변경은 먼저 묻는다
- [예시] 🚫 실제 결제 연동, 실서버 데이터 삭제, 비밀번호·키를 코드나 문서에 넣기

## 10. 관련된 사람 · 시스템
- 누가 결정하고, 누가 검토하고, 어떤 시스템과 닿는지
- [예시] 결정: 이사님 · 기술 검토: 개발팀 · 운영: 예약 담당 · 연동 후보: 기존 회원 명단(1차는 수동 업로드)

## 11. 단계 계획 (작게)
- 1단계에서 확인할 것 → 2단계에서 늘릴 것
- [예시] 1단계(시험): 특가 목록·상세·문의 폼 + 담당자 문의함 / 내부 직원만 테스트
- [예시] 2단계: 관리자 특가 등록 화면, 마감 자동 처리 / 3단계(검토 후): 회원 대상 공개

## 12. 아직 모르는 것 (질문 목록)
- 정해지지 않은 것과 누가 언제 답할지
- [예시] 남은 객실 수를 정확히 보여 줄지, "얼마 안 남음"으로만 보여 줄지 → 이사님, 1단계 전
- [예시] 문의 회신 목표 시간 → 예약 담당, 1단계 중

## 13. 결정 기록
| 날짜 | 결정 | 이유 | 결정한 사람 |
|---|---|---|---|
| [예시] 10/27 | 1차에는 결제 제외 | 파트너 정산 방식 미확정 | 이사님 |
```

**쓰는 요령**
- 처음부터 다 채우지 않으셔도 됩니다. 1, 2, 4, 5, 7, 9번만 있어도 시작할 수 있습니다.
- 기술 용어는 몰라도 됩니다. 8번은 "이런 화면이 있었으면" 수준이면 충분하고, 나머지는 개발팀과 AI가 기술 계획서에서 채웁니다.
- 한 장 반을 넘기면 나눌 때가 된 것입니다. 1단계 PRD와 2단계 PRD로 나눕니다.

### 3-4. 'AI가 나에게 물어봐야 할 질문' 체크리스트

AI에게 "아래 질문 중 아직 답이 없는 것만 한 번에 3~5개씩 물어봐 줘"라고 하시면 됩니다.

**문제·목적**
- [ ] 지금 무엇이 불편한가요? 누가, 얼마나 자주 겪나요?
- [ ] 이걸 안 만들면 무엇을 잃나요? 이걸로 무엇이 좋아지면 성공인가요?
- [ ] 비슷한 걸 이미 쓰고 있거나 해 본 적이 있나요?

**사용자·흐름**
- [ ] 주로 누가 쓰나요? 고객, 직원, 관리자 중 누구인가요? 휴대폰인가요, PC인가요?
- [ ] 처음부터 끝까지 한 번 쓰는 흐름을 말로 설명해 주세요.
- [ ] 가장 자주 일어나는 상황과, 드물지만 곤란한 상황(취소, 중복, 마감 후 문의 등)은 무엇인가요?

**범위**
- [ ] 1단계에 꼭 있어야 할 것 3가지는 무엇인가요?
- [ ] 이번에 일부러 빼는 것은 무엇인가요?
- [ ] 언제까지 무엇을 보고 싶으신가요?

**완료·확인**
- [ ] 완성되었다는 걸 무엇을 보고 판단하시겠어요?
- [ ] 직접 눌러 보고 싶은 장면 3개는 무엇인가요?

**데이터·연동**
- [ ] 어떤 정보가 들어가고 나오나요? 지금 그 정보는 어디에 있나요(엑셀, 메일, 다른 시스템)?
- [ ] 다른 시스템과 연결해야 하나요? 1차는 수동으로 해도 되나요?

**권한·위험**
- [ ] 고객 정보, 돈, 계약 수치가 들어가나요? 누가 볼 수 있어야 하나요?
- [ ] 자동으로 하면 안 되고 꼭 사람이 확인해야 하는 행동은 무엇인가요(외부 발송, 결제, 삭제)?
- [ ] 절대 하면 안 되는 것은 무엇인가요?

**사람·결정**
- [ ] 최종 결정은 누가 하나요? 개발팀 검토는 누가 하나요?
- [ ] 아직 정하지 못한 것은 무엇이고, 누가 언제 정하나요?

### 3-5. 흔한 실수

| 실수 | 왜 문제인가 | 이렇게 바꿉니다 |
|---|---|---|
| 한 줄로 "○○ 만들어 줘" | AI가 빈칸을 마음대로 채워 그럴듯하지만 엉뚱한 결과가 나온다(14:48) | AI 인터뷰로 PRD 한 장부터 쓴다 |
| 해결책부터 쓰기("앱 만들어서…") | 진짜 문제를 놓치고, 더 쉬운 방법을 못 본다 | 2번 '왜 하나요'를 먼저 쓴다 |
| 비목표가 없음 | 결제, 회원가입, 다국어까지 다 만들어 일정과 비용이 늘어난다(S10) | '이번에 안 하는 것'을 3개 이상 적는다 |
| "편하게, 예쁘게, 빠르게" | 확인할 수 없는 말이라 끝이 없다 | "~하면 ~된다"로 바꾼다 |
| 한 번에 전부 자동화 | 이도 저도 안 된다(26:56) | 1단계는 흐름 하나만 |
| 작은 일에도 문서 산더미 | 검토할 문서가 일보다 커진다(S10) | 한 문장으로 설명되는 일은 바로 시킨다(S3) |
| "다 됐어요"를 믿기 | 겉보기만 되고 예외 상황에서 깨진다 | 캡처, 테스트 결과, 직접 눌러 보기로 확인 |
| 한 대화를 며칠씩 끌기 | 틀린 시도가 쌓여 AI가 헷갈린다(S3) | 결정은 문서에 옮기고 새 대화로 다시 시작 |
| 금지선이 없음 | 메일 발송, 데이터 삭제, 키 노출 같은 사고가 난다(S7, S9) | 9번 칸을 반드시 채운다 |
| 모든 정보를 모든 에이전트에게 | 비용이 늘고 정보가 샌다(25:56) | 업무별로 필요한 것만 준다 |
| 결정을 기억에만 둔다 | 사람이나 AI가 바뀌면 같은 논쟁을 반복한다 | 결정 기록 한 줄씩(S12) |
| 기술까지 이사님이 정하려 함 | 시간이 들고, 개발팀의 판단을 막는다 | '무엇'은 이사님, '어떻게'는 개발팀 |

### 3-6. 복사해서 쓰는 PRD 인터뷰 시작 프롬프트

```text
너는 경험 많은 PM이야. 나는 개발을 모르는 임원이고, 아래 아이디어로 개발팀과 AI 에이전트에게 넘길 PRD를 만들고 싶어.

아이디어: <한두 줄로 적기. 손메모 사진이 있으면 함께 첨부>

진행 방법:
1. 바로 문서를 쓰지 말고 먼저 나를 인터뷰해 줘. 한 번에 질문 3~5개만, 쉬운 말로 물어봐 줘.
2. 문제, 사용자, 목표와 성공 기준, 이번에 안 하는 것, 핵심 흐름, 완료 기준("~하면 ~된다"), 금지선(항상/먼저 묻기/절대 금지), 아직 모르는 것을 빠짐없이 물어봐 줘.
3. 내가 모른다고 하면 선택지 2~3개를 장단점과 함께 제안해 줘.
4. 다 물어본 뒤에 아래 목차로 PRD 초안을 써 줘: 한 줄 요약 / 왜 하나요 / 누가 쓰나요 / 목표와 성공 기준 / 이번에 안 하는 것 / 핵심 흐름 / 완료 기준 / 화면·데이터 / 금지선 / 관련된 사람·시스템 / 단계 계획 / 아직 모르는 것 / 결정 기록.
5. 기술 선택은 정하지 말고, 개발팀에 물어볼 질문 목록으로 따로 적어 줘.
6. 실제 요금, 계약 수치, 고객 개인정보는 문서에 넣지 말고 "별첨 참조"로 표시해 줘.
```
