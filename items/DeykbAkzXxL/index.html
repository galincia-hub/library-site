핵심 요지

Claude 사용량이 빨리 바닥나는 원인은 '많이 써서'가 아니라 불필요한 파일 탐색과 원본 로그·출력을 그대로 주고받는 토큰 낭비라는 주장. 이를 줄이는 Claude Code 플러그인 3종을 소개한다. 영상이 다루는 것은 프롬프팅 기법이 아니라 도구다. 다만 각 도구의 원리는 프롬프트 원칙으로 옮겨 쓸 수 있다.

주요 내용

1. Ponytail(포니테일) (github.com/DietrichGebert/ponytail): "가장 게으른 시니어 개발자처럼" 최소 구현(YAGNI)을 하도록 에이전트를 유도하는 스킬/플러그인. 원리: 출력 최소화.

2. Graphify (github.com/Graphify-Labs/graphify): 코드베이스·문서를 로컬 지식그래프(graph.json)로 만든다. Claude가 grep이나 파일 통독 대신 그래프를 질의해 필요한 부분만 읽게 한다. 원리: 지도 먼저, 필요한 곳만 읽기.

3. Headroom (github.com/headroomlabs-ai/headroom): 도구 출력·로그·RAG 청크·대화 이력을 LLM에 보내기 전에 로컬에서 압축하는 프록시/MCP. 원본은 필요할 때 다시 꺼낼 수 있다(CCR). 원리: 입력 압축, 필요한 부분만 통과.

  • 영상 말미에서 세 가지를 한 번에 설치하는 가이드를 홍보한다(제거).

수치/주장 확인

  • "Ponytail GitHub 9만 스타": 이번에 별도 확인하지 못함(미검증). 인기 저장소인 것은 맞다.
  • "Ponytail이 사용량을 50% 넘게 줄인다(화면 128K→52K, -59%)": 과장. 공식 벤치(2026-10-07, 39과제, Opus 5.5)는 출력 토큰 -45%, 비용 -26%, 코드 -53%다. JetBrains 독립 테스트(80과제)는 비용 -10.3%, 코드 -15%에 그쳤다. 절감 효과는 과잉 구현 성향이 큰 과제에 집중된다.
  • "Graphify를 쓰면 토큰을 70% 넘게 덜 쓴다": 근거가 다름. 공식 '71.5배'는 전체 파일 통독과 그래프 질의를 비교한 추정치(단어/문자 기반 추산)이고, 실제 엔드투엔드 측정이 아니다. ERPNext 에이전트 비교(Graphify 측 게시)에서는 정확도 82% vs 70.8%(+11pt)였지만 비용은 사실상 같았다($0.320 vs $0.322). "70% 절감"이 일반적으로 성립한다고 보기 어렵다.
  • "Headroom이 불필요한 줄을 압축해 같은 결과": 부분 사실. JSON 도구 출력·로그·긴 세션에서 효과가 크다. 소스코드, 짧은 메시지, 시스템 프롬프트, grep 결과는 대부분 압축하지 않는다(공식 Limitations). 압축은 로컬에서 하고 원본은 복구할 수 있다.
  • "며칠 만에 바닥나는 건 토큰 누수 때문": 의견. 일리는 있지만 정량 근거는 제시하지 않았다.

시사점

  • 그록봇/Orca/서르카 운영: 세 원리(출력 최소화·지도 우선 탐색·입력 압축)는 플러그인을 설치하지 않아도 지시문 규칙으로 바로 적용할 수 있다. 주간 한도 절약 목표와 맞는다. 실제 설치(특히 Headroom 프록시처럼 트래픽을 경유시키는 방식)는 권한·보안 검토와 Owner 승인이 필요하다.
  • Cruise International: 직접 관련은 낮다. 다만 같은 원칙을 일반 업무 프롬프트(요약·견적·고객 응대 초안)에 적용하면 응답 길이와 비용을 줄일 수 있다 → combined_prompt.md 참고.
  • 마케팅: 댓글 키워드→DM 퍼널(댓글 1,698)의 또 다른 사례.
  • 투자: 관련 없음.

Research Level 1: 원리는 프롬프트 규칙으로 즉시 채택한다. 도구 설치는 벤치 수치가 과장돼 있고 프록시 보안 이슈가 있어 보류하며, 필요 시 Graphify(로컬·결정적 빌드)부터 소규모로 시험한다.

combined_prompt.md

3원칙 통합 프롬프트 (Ponytail · Graphify · Headroom 원리 적용)

> 사용법: [대괄호] 부분만 바꿔 붙여넣으세요. 자료가 길면 [자료]에 원문을 넣으면 됩니다. 모델은 먼저 '지도(목차)'만 만들고, 필요한 부분만 골라 압축해 읽은 뒤, 가장 짧은 결과만 냅니다. 출력 분량 제한은 [분량]으로 조절합니다.

너는 토큰을 아끼는 실무자다. 아래 3원칙을 순서대로 지켜라.

[목표] [주제/해야 할 일]
[독자·용도] [누가 어디에 쓰는지]
[자료] [원문·로그·파일 목록·링크 — 없으면 "없음"]
[분량] [예: 5줄 이내 / 표 1개]

1) 지도 먼저 (Graphify 원칙)
- 자료 전체를 다시 쓰지 말고, 먼저 구성 요소와 관계를 3~7개 항목의 '지도'로만 정리하라.
- 목표에 필요한 항목만 골라 표시하고, 나머지는 읽지도 인용하지도 마라.

2) 입력 압축 (Headroom 원칙)
- 고른 항목에서 반복·로그·서식·인사말·중복 수치를 제거하고 핵심 사실만 남겨라.
- 버린 정보 중 나중에 필요할 수 있는 것은 "보관: …" 한 줄로만 표시하라(원문 복구 가능하게).

3) 출력 최소화 (Ponytail 원칙)
- 요청받지 않은 기능·대안·배경설명·사족을 만들지 마라 (YAGNI).
- 가장 단순하게 목표를 달성하는 결과 하나만 [분량] 안에서 내라.
- 위험하거나 불확실한 부분만 "확인 필요:"로 1~2줄 남겨라.

출력 형식:
[지도] (선택한 항목에 ✔)
[결과]
[확인 필요]

---

예시: Cruise International 적용

너는 토큰을 아끼는 실무자다. 아래 3원칙을 순서대로 지켜라.

[목표] 2027년 봄 지중해 크루즈 단체(기업 인센티브 30명) 제안서의 핵심 요약과 고객 회신 메일 초안 작성
[독자·용도] 고객사 인사팀 담당자에게 보낼 1차 회신 (발송 전 이사님 확인용 초안)
[자료] 선사 3곳의 일정표·요금표 PDF 텍스트, 지난주 고객 문의 메일 내용, 내부 메모(객실 블록 가능 여부)
[분량] 요약 5줄 + 메일 본문 10줄 이내

1) 지도 먼저 (Graphify 원칙)
- 자료 전체를 다시 쓰지 말고, 먼저 구성 요소와 관계를 3~7개 항목의 '지도'로만 정리하라.
- 목표에 필요한 항목만 골라 표시하고, 나머지는 읽지도 인용하지도 마라.

2) 입력 압축 (Headroom 원칙)
- 고른 항목에서 반복·로그·서식·인사말·중복 수치를 제거하고 핵심 사실만 남겨라.
- 버린 정보 중 나중에 필요할 수 있는 것은 "보관: …" 한 줄로만 표시하라.

3) 출력 최소화 (Ponytail 원칙)
- 요청받지 않은 기능·대안·배경설명·사족을 만들지 마라 (YAGNI).
- 고객 조건(인원·시기·예산)에 맞는 추천 1안과 예비 1안만 [분량] 안에서 내라.
- 요금·객실 확보·비자 등 불확실한 부분만 "확인 필요:"로 1~2줄 남겨라.

출력 형식:
[지도] (선택한 항목에 ✔)
[결과] 요약 5줄 / 메일 초안
[확인 필요]
